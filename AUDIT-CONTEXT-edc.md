## Phase 1 -- Initial Orientation

### 1.1 What Veil Is

Veil ("clvm-zk") is a **privacy-preserving zkVM layer for Chialisp**. It lets users evaluate Chia's CLVM programs inside zero-knowledge proofs so that:

- An observer sees that *a valid program ran* and *produced certain conditions*, but not the program inputs.
- Coins are represented as *commitments* in a Merkle tree; spending reveals a *nullifier* (to prevent double-spends) but not the coin itself.
- Optionally, coins carry a *TAIL hash* identifying a "Chia Asset Token" (CAT) asset type; the TAIL program must authorize every spend.
- Settlement proofs enable trustless two-party atomic exchanges ("offers") without revealing either party's coin details.

**Status**: WIP research project. Core + offers infrastructure complete; settlement end-to-end testing ongoing.

### 1.3 Feature Flags

- **Exactly one backend** must be enabled: `risc0`, `sp1`, or `mock`.  Compile-time enforcement via `compile_error!` for mutual exclusion and "at least one" guards.
- `testing` (enabled by default alongside `sp1`) -- enables `testing_helpers` module and `sha2-hasher` on core.
- `debug-logging` -- optional eprintln diagnostics in `Spender`.

## Phase 2 -- Ultra-Granular Module Analysis

### 2.1 clvm_zk_core

**Role**: `#![no_std]` core library shared between host and guest. Contains all shared types, CLVM parsing, operator definitions, commitment/nullifier computation, Merkle verification, and evaluation bridge.

#### 2.1.1 Types (`types.rs`)

##### `ProgramParameter`
- Variants: `Int(u64)`, `Bytes(Vec<u8>)`.
- Derives both `serde` and `borsh` -- dual serialization.
- `ProgramParameter::int(value: i64)` casts `i64` to `u64` -- **assumption**: negative CLVM values are represented as two's complement in u64.

##### `ClvmValue`
- `Atom(Vec<u8>)` or `Cons(Box<ClvmValue>, Box<ClvmValue>)`.
- Standard CLVM tree representation.
- `PartialEq` derived -- structural equality.

##### `Input` (Guest Input)
- Contains `chialisp_source: String` (raw source, compiled inside guest).
- `coin_mode: CoinMode` -- discriminated union: `Execute`, `Spend(SerialCommitmentData)`, `Mint(MintData)`.
- `tail_hash: Option<[u8; 32]>` -- None or zeros = XCH, Some(nonzero) = CAT.
- `tail_source: Option<String>` -- TAIL program source for CAT authorization.
- `tail_params: Vec<ProgramParameter>` -- params for TAIL program execution.
- `additional_coins: Option<Vec<AdditionalCoinInput>>` -- for ring spends (multi-coin atomic).

**Invariants**:
1. If `tail_hash != [0;32]` and `coin_mode == Spend`, then `tail_source` MUST be Some.
2. All additional coins in a ring MUST have the same `tail_hash` as the primary.
3. `leaf_index` is `u64` for cross-platform borsh compat (guest is 32-bit RISC-V).

##### `ProofOutput` (Guest Journal)
- `program_hash: [u8; 32]` -- hash of compiled bytecode template.
- `nullifiers: Vec<[u8; 32]>` -- empty for Execute mode, 1 for single spend, N for ring spend.
- `clvm_res: ClvmResult` -- `output: Vec<u8>` (serialized CLVM) + `cost: u64`.
- `proof_type: u8` -- borsh-skipped, always 0 in guest. The host-side `PrivateSpendBundle` carries the richer `ProofType` enum.
- `public_values: Vec<Vec<u8>>` -- extensible public data (currently unused in most flows).

**Invariant**: `program_hash` is the hash of the *compiled template bytecode*, not the source string. Parameter names don't affect it.

##### `SerialCommitmentData`
- All fields needed for spend verification: `serial_number`, `serial_randomness`, `merkle_path`, `coin_commitment`, `serial_commitment`, `merkle_root`, `leaf_index`, `program_hash`, `amount`.
- `leaf_index: u64` (not usize) for cross-platform consistency.

##### `MintData`
- Controls CAT issuance: `tail_source`, `tail_params`, `output_puzzle_hash`, `output_amount`, `output_serial`, `output_rand`.
- Optional `genesis_coin: Option<GenesisSpend>` for single-issuance CATs.
- **Status**: Mint mode is declared in types but host backends reject it ("not yet implemented").

##### `CoinMode`
- Enum: `Execute` (pure program run), `Spend(SerialCommitmentData)`, `Mint(MintData)`.
- Ensures spend and mint are mutually exclusive at the type level.

##### `AggregatedOutput`
- `nullifiers`, `conditions`, `commitments` -- used by recursive aggregation guest output.

#### 2.1.2 CLVM Parser (`clvm_parser.rs`)

**Purpose**: Deserializes binary CLVM format into `ClvmValue` tree.

**Algorithm**: Streaming parser with positional tracking (`pos` field).

| Byte Range | Encoding |
|---|---|
| `0x00-0x7F` | Single-byte atom |
| `0x80` | Nil (empty atom) |
| `0x81-0xBF` | Multi-byte atom, size in lower 6 bits (1-63 bytes) |
| `0xC0-0xDF` | 2-byte size (64-8191 bytes) |
| `0xE0-0xEF` | 3-byte size (8192-1048575 bytes) |
| `0xF0-0xF7` | 4-byte size |
| `0xF8-0xFF` | 5-byte size (uses u64 to avoid 32-bit overflow) |
| `0xFF` | Cons pair marker |

**Invariants**:
1. Parser never reads beyond `self.bytes.len()`.
2. Recursive descent -- deep nesting could cause stack overflow (no explicit depth limit).
3. The `0xF8-0xFF` branch overlaps with the `0xFF` cons marker -- but `0xFF` is handled first in the match statement due to ordering (the `0x00..=0x7F` arm comes before `0x80..=0xBF`, and then subsequent ranges; however, `0xF8..=0xFF` is AFTER `0xFF` as cons pair -- **wait**: looking more carefully, `0xFF` matches the FIRST arm (`0xFF => { // cons pair }`), so the `0xF8..=0xFF` range in the later arm will never match `0xFF`. This is correct but subtle -- the match arms are ordered so `0xFF` is caught by the explicit cons pair arm before the range arm.

**Assumption**: All CLVM bytecode is well-formed. Malformed bytecode returns `Err(&'static str)`.

#### 2.1.3 Operators (`operators.rs`)

**Purpose**: Single source of truth for CLVM opcodes, shared between host compilation and guest evaluation.

Notable mappings:
- `Remark` and `Quote` both map to opcode 1 -- **observation**: `Remark` opcode (1) overlaps with `Quote` opcode (1). The `from_opcode(1)` method returns `Quote`. This means `Remark` can never be parsed from opcode bytes; it's only accessible by string name. This is likely intentional since `Remark` in Chia is indeed opcode 1 as a condition code (not a CLVM operator).
- `Modulo` maps to opcode 61, and `ModPow` to 60. `CreateCoinAnnouncement` also maps to 60, `AssertCoinAnnouncement` to 61. This means opcode 60/61 are **overloaded** between extended math operations and announcement conditions. In `from_opcode()`, opcode 60 -> `ModPow` and opcode 61 -> `Modulo`, which means announcements can never be parsed from opcodes. In practice, announcement conditions are identified by numeric value in the condition list, not via the operator enum.
- Custom opcodes: `BlsVerify` = 59, `EcdsaVerify` = 200, `CallFunction` = 150.

**Arity definitions**: Used for validation. `CreateCoin` arity = 2, but in practice the guest handles 2-arg (transparent) and 4-arg (private) modes. The arity check may not be enforced in evaluation.

#### 2.1.4 Coin Commitment (`coin_commitment.rs`)

##### `SerialCommitment`
- `compute(serial_number, serial_randomness, hasher)`:
  - Domain: `b"clvm_zk_serial_v1.0"` (19 bytes)
  - Layout: `domain || serial_number || serial_randomness` (19 + 32 + 32 = 83 bytes)
  - Result: 32-byte hash

##### `CoinCommitment`
- `compute(tail_hash, amount, program_hash, serial_commitment, hasher)`:
  - Domain: `b"clvm_zk_coin_v2.0"` (17 bytes)
  - Layout: `domain || tail_hash || amount_be || puzzle_hash || serial_commitment` (17 + 32 + 8 + 32 + 32 = 121 bytes)
  - `build_coin_commitment_preimage()` provides zero-allocation version for guest use.

**Invariants**:
1. Different `tail_hash` values produce different commitments (asset type isolation).
2. `XCH_TAIL = [0u8; 32]` is the sentinel for native currency.
3. Amount is big-endian encoded.
4. The preimage is deterministic: same inputs always produce same commitment.

##### `CoinSecrets`
- Stores `serial_number` and `serial_randomness`.
- `serial_number()` returns the serial number used as part of nullifier computation.
- **Critical**: losing CoinSecrets = permanent fund loss.

#### 2.1.5 Merkle Tree (`merkle.rs`)

- `SparseMerkleTree`: append-only Merkle tree.
- Depth bounded: `MIN_TREE_DEPTH=1`, `MAX_TREE_DEPTH=64`.
- Empty nodes use precomputed hashes: `empty_leaf = hash("EMPTY_LEAF")`, then `empty_node[i] = hash(empty_node[i-1] || empty_node[i-1])`.
- Proof generation: for each level, collects sibling hash (actual leaf value or precomputed empty hash).
- Verification: walks path from leaf to root, ordering left/right by `index & 1`.

**Invariants**:
1. Tree is append-only; no deletion of leaves.
2. Root is recomputed on every insertion (full recomputation from leaves -- **O(n * depth)** per insert).
3. Proof path length == tree depth (fixed, not variable).
4. `MAX_MERKLE_PROOF_DEPTH = 64` is also enforced in `verify_merkle_proof()` in `lib.rs`.

**Assumption**: The `compute_node_hash()` method is recursive with depth up to `self.depth` and width up to `self.leaves.len()`. For large trees (millions of leaves), this is **exponential** in depth due to lack of caching. This is acceptable for the simulator (test use) but would not scale for production.

#### 2.1.6 Core Library Functions (`lib.rs`)

##### Compilation
- `compile_chialisp_to_bytecode(hasher, source)` -- delegates to `clvm_tools_rs::compile_chialisp()`, then hashes result.
- `compile_chialisp_template_hash_default(source)` -- SHA-256 variant (requires `sha2-hasher` feature).
- **Key property**: Parameter names in source do NOT affect bytecode hash. `(mod (x y) (+ x y))` and `(mod (a b) (+ a b))` produce identical bytecode.

##### Number Encoding
- `atom_to_number(ClvmValue)` -- big-endian to i64. No sign handling for multi-byte atoms (assumes positive).
- `number_to_atom(i64)` -- handles: 0 -> empty atom, 1-127 -> single byte, larger values -> big-endian with sign-bit handling (leading 0x00 for positive numbers where MSB is set, 0x80 OR for negative).
- `parse_variable_length_amount(bytes)` -- pads to 8 bytes big-endian, returns u64. Max 8 bytes.

##### CLVM Value Encoding
- `encode_clvm_value(ClvmValue)` -- serializes to binary CLVM format. Matches parser ranges.
- `is_clvm_nil(output)` -- `[]` or `[0x80]` is nil.

##### Condition Parsing
- `deserialize_clvm_output_to_conditions(output)` -- parses CLVM bytes to `Vec<Condition>`.
- Handles both single conditions and lists of conditions.
- `extract_args_from_list()` -- only accepts atoms as args; cons pairs in arg position cause error.

##### Announcement Processing
- `process_announcements(conditions, puzzle_hash, coin_id, hasher)`:
  - Collects CREATE_PUZZLE_ANNOUNCEMENT: `hash = hasher(puzzle_hash || message)`.
  - Collects CREATE_COIN_ANNOUNCEMENT: `hash = hasher(coin_id || message)` (skipped if no coin_id).
  - Verifies all ASSERT_* hashes match a CREATE_* hash.
  - Filters announcement conditions from output.
  - **Linear search**: assertion satisfaction check is O(assertions * announcements).

##### Balance Enforcement
- `enforce_ring_balance(private_inputs, conditions)`:
  - Sums all CREATE_COIN amounts from conditions (opcodes 51 with 2 or 4 args).
  - Sums all input amounts from `CoinMode::Spend` data.
  - **Critical rule**: `total_output_amount > total_input_amount` -> error ("inflation").
  - Allows `output < input` (burning/fees).
  - Verifies all additional coins have same `tail_hash` as primary ("single-asset ring").
  - **Runs BEFORE CREATE_COIN transformation** (which replaces 4-arg conditions with commitments).
  - Rejects `Mint` mode (must use dedicated mint validation).

##### Commitment Computation Helpers
- `compute_serial_commitment(hasher, serial_number, serial_randomness)` -- fixed-size buffer, no allocation.
- `compute_coin_commitment(hasher, tail_hash, amount, puzzle_hash, serial_commitment)` -- fixed-size buffer.
- `compute_nullifier(hasher, serial_number, program_hash, amount)` -- `Vec` allocation (72 bytes).

**Invariant**: Nullifier = `hash(serial_number || program_hash || amount)`. Different programs or amounts produce different nullifiers from the same serial number.

##### Merkle Proof Verification (standalone)
- `verify_merkle_proof(hasher, leaf_hash, merkle_path, leaf_index, expected_root)`:
  - Path depth bounded by `MAX_MERKLE_PROOF_DEPTH = 64`.
  - Uses `is_multiple_of(2)` for left/right ordering (nightly feature: `int_roundings`).
  - Fixed-size combined buffer: `[0u8; 64]`.

##### ECDSA Verification
- `verify_ecdsa_signature_with_hasher(hasher, pubkey, message, signature)`:
  - Accepts 33 or 65 byte public keys (compressed/uncompressed).
  - Signature MUST be exactly 64 bytes (compact format). **No padding of short signatures** -- explicit security decision.
  - Messages: 32 bytes treated as pre-hashed; longer messages are hashed first.
  - Returns `Ok(true/false)`, not `Err` on signature mismatch.

##### BLS Verification
- Not in core (`clvm_zk_core`); implemented per-backend:
  - Mock: uses `blst` crate (min_sig variant: pk in G2 96 bytes, sig in G1 48 bytes).
  - SP1 guest: uses `bls12_381` crate with pairing check.
  - RISC-0 guest: uses `risc0-zkvm` accelerated precompiles.

##### Modular Exponentiation
- `modular_pow(base, exponent, modulus)`:
  - `modulus == 0` returns 0 (convention, not mathematically meaningful).
  - Uses i128 intermediate to prevent overflow.
  - Binary exponentiation.

#### 2.1.7 Backend Utilities (`backend_utils.rs`)

- `convert_proving_error()` -- transforms zkVM errors into user-friendly messages.
- `validate_proof_output()` -- checks `clvm_res.output` is not empty.
- `validate_nullifier_proof_output()` -- additionally checks nullifiers are present and non-zero.

### 2.2 Protocol Layer

**Location**: `src/protocol/`

#### 2.2.1 Structures (`structures.rs`)

##### `ProofType`
- Enum: `Transaction(0)`, `ConditionalSpend(1)`, `Settlement(2)`, `Mint(3)`.
- Only `Transaction`, `Settlement`, and `Mint` are "submittable" to blockchain.
- `ConditionalSpend` is "locked" -- must be wrapped in settlement proof.

##### `PrivateCoin`
- Fields: `puzzle_hash`, `amount`, `serial_commitment: SerialCommitment`, `tail_hash`.
- Factory methods:
  - `new_with_secrets(puzzle_hash, amount)` -- generates random serial_number + randomness, returns `(coin, CoinSecrets)`.
  - `new_random(puzzle_hash, amount)` -- discards secrets (**coin is unspendable**).
  - `new_with_secrets_and_tail()` -- CAT variant.
- Validation: rejects all-zero puzzle_hash and all-zero serial_commitment.
- `is_xch()` / `is_cat()` -- checks tail_hash.

##### `PrivateSpendBundle`
- Fields: `zk_proof`, `nullifiers: Vec<[u8; 32]>`, `public_conditions`, `proof_type`.
- Validation: non-empty proof, at least one nullifier, no all-zero nullifiers.
- `extract_created_coins()` -- parses CREATE_COIN conditions:
  - 1 arg (32 bytes) -> `Private { commitment }`
  - 2 or 4 args -> `Transparent { puzzle_hash, amount }`
  - **Other arg counts silently skipped** (no error).
- `is_submittable()` -- Transaction, Settlement, or Mint.
- `is_conditional()` -- ConditionalSpend only.

##### `CreatedCoinOutput`
- `Private { commitment }` or `Transparent { puzzle_hash, amount }`.

#### 2.2.2 Puzzles (`puzzles.rs`)

##### `create_signature_puzzle()`
- Returns `(mod (pubkey message signature) (list (list 49 pubkey message signature)))`.
- Outputs AGG_SIG_UNSAFE condition for backend-side signature verification.
- Hash is deterministic (compiled template hash).

##### `create_password_puzzle()`
- Returns `(mod (a b) (= (sha256 a) b))`.
- Takes password preimage and expected hash as params.

##### `create_password_puzzle_program(password)`
- Embeds the hash: `(= (sha256 a) 0x{hash})`.
- Hash is computed host-side from the password string.

##### `create_delegated_puzzle()`
- Settlement-specific delegated puzzle.
- Takes 7 params: offered, requested, maker_pubkey, change_amount, change_puzzle, change_serial, change_rand.
- Outputs CREATE_COIN for change + settlement terms.

##### `create_settlement_assertion_puzzle()`
- Similar to delegated puzzle but uses `list` instead of `c` for output structure.
- Outputs: `((51 change_puzzle change_amount change_serial change_rand) (offered requested maker_pubkey))`.

##### `compile_to_template_bytecode(source)`
- Compiles Chialisp to bytecode without parameter substitution.
- Used for delegated puzzle delegation.

**Invariant**: All puzzle compilation goes through `clvm_tools_rs::compile_chialisp()`. The hash of compiled bytecode is the program identity.

#### 2.2.3 Spender (`spender.rs`)

##### `Spender::create_spend_with_serial()`
- Primary spend flow for single-coin transactions.
- Steps:
  1. Validate coin.
  2. Compute `CoinCommitment` from coin data.
  3. Determine `tail_hash` (None for XCH, Some for CAT).
  4. Call `ClvmZkProver::prove_with_serial_commitment()`.
  5. Extract nullifiers from proof output.
  6. Construct and validate `PrivateSpendBundle`.

**Assumption**: The proof backend correctly computes the nullifier inside the guest. The host does not independently verify the nullifier value.

##### `Spender::create_ring_spend()`
- Multi-coin atomic spend (for CATs).
- Steps:
  1. Verify all coins have same `tail_hash`.
  2. Validate all coins.
  3. Compute `CoinCommitment` for each.
  4. Pack primary + additional coins into `AdditionalCoinInput` structs.
  5. Call `ClvmZkProver::prove_ring_spend()`.
  6. Verify nullifier count == coin count.
  7. Construct `PrivateSpendBundle` with all nullifiers.

**Invariant**: Ring spend produces exactly N nullifiers for N input coins.

##### `Spender::create_conditional_spend()`
- Same as `create_spend_with_serial()` but sets `ProofType::ConditionalSpend`.
- Uses only the first nullifier (single-nullifier for conditional spends).
- Used for creating offer maker proofs.

##### `Spender::verify_nullifier()`
- Checks if a bundle contains a specific nullifier.
- Simple `Vec::contains()` check.

#### 2.2.4 Settlement (`settlement.rs`)

##### `SettlementOutput`
- Contains: `maker_nullifier`, `taker_nullifier`, `maker_change_commitment`, `payment_commitment`, `taker_goods_commitment`, `taker_change_commitment`, `maker_pubkey`.
- 6 commitments + 2 nullifiers + 1 public key = the complete settlement state.

##### `SettlementParams`
- Everything the taker needs: maker's proof, taker's coin, secrets, merkle data, payment parameters, asset type info.

##### `prove_settlement()`
- **V2 architecture**: no recursive verification of maker's proof inside guest. Instead:
  1. Host extracts maker's journal (public values).
  2. Host parses maker's CLVM output to get settlement terms.
  3. Host constructs `SettlementInput` struct.
  4. Guest receives `SettlementInput`, computes commitments, outputs `SettlementOutput`.
  5. **Validator must verify BOTH proofs independently** and check consistency.

- Flow (risc0 path):
  1. Deserialize maker's receipt (borsh).
  2. Decode maker's journal -> `ProofOutput`.
  3. Extract maker's nullifier.
  4. Parse maker's CLVM output -> `(maker_change_commitment, offered, requested, maker_pubkey)`.
  5. Build `SettlementInput` with taker's data.
  6. Run settlement guest ELF.
  7. Decode `SettlementOutput` from receipt.
  8. Return `SettlementProof`.

- Flow (sp1 path): Analogous but uses `SP1ProofWithPublicValues` / `bincode` instead of `Receipt` / `borsh`.

- **Mock backend**: Settlement not supported ("requires risc0 or sp1").

##### Host-Side CLVM Parsing (settlement helpers)
- `parse_maker_clvm_output()` -- deeply nested pattern matching on `ClvmValue` to extract CREATE_COIN + settlement terms.
- `extract_create_coin_commitment_host()` -- recomputes coin commitment from (puzzle, amount, serial, rand) using v2.0 format with hardcoded domain separators.
- `extract_settlement_terms_host()` -- extracts (offered, requested, maker_pubkey).
- `extract_bytes_32_host()` -- atom to `[u8; 32]`.
- `extract_u64_host()` -- CLVM big-endian atom to u64.

**Invariants**:
1. Maker's proof must be `ConditionalSpend` type.
2. Settlement terms are PUBLIC (extracted from maker's journal which was public when offer was posted).
3. Atomicity: validator checks both proofs together.

#### 2.2.5 Recursive Aggregation (`recursive.rs`)

##### `AggregatedProof`
- Host-side struct: `zk_proof`, `nullifiers`, `conditions`, `proof_count`.
- Wraps the recursive proof output.

- `AggregatedOutput` is re-exported from `clvm_zk_core`.

### 2.3 Wallet Layer

**Location**: `src/wallet/`

#### 2.3.1 HD Wallet (`hd_wallet.rs`)

##### `CLVMHDWallet`
- BIP32 HD key derivation from seed.
- Seed validation: 16-64 bytes. Seeds != 32 bytes are SHA-256 hashed to 32 bytes first.
- Derivation path: `m/44'/coin_type'/account_index'/0'` (all hardened).
- Coin types: Mainnet = 8444 (Chia), Testnet = 1.

##### `AccountKeys`
- Derived keys:
  - `spending_key = hash("clvm_zk_spend_auth_v1" || account_bytes || network)`.
  - `viewing_key = hash("clvm_zk_view_key_v1" || spending_key)`.
  - `nullifier_key = hash("clvm_zk_nullifier_key_v1" || spending_key)`.
  - `stealth_keys` -- derived from `hash("clvm_zk_stealth_seed_v1" || account_bytes)`.
- All derivations are SHA-256 based, deterministic.

**Assumption**: `viewing_key` is derived FROM `spending_key` via hash. Knowing viewing_key does NOT reveal spending_key (one-way). However, in stealth address mode, view key holders CAN spend (documented security warning).

##### `WalletPrivateCoin`
- Wraps `PrivateCoin` + `CoinSecrets` + wallet metadata.
- `new()` -- creates coin with random secrets.
- `new_with_tail()` -- CAT variant.

##### `ViewOnlyWallet`
- From `ViewingKey`, can derive viewing tags and check them.
- Cannot spend.

#### 2.3.2 Stealth Addresses (`stealth.rs`)

##### Security Model
- **CRITICAL**: View key holders CAN spend coins in nullifier mode. This is a deliberate design tradeoff for performance (~200x faster than ECDH). The documentation explicitly warns against sharing view keys with untrusted parties.

##### Scheme
- **Hash-based stealth** (not ECDH-based):
  - Sender picks nonce, computes `shared_secret = hash("stealth_v1" || view_pubkey || nonce)`.
  - All stealth coins use the same trivial puzzle: `(mod () ())` -- security comes from nullifier protocol, not puzzle logic.
  - `STEALTH_NULLIFIER_PUZZLE_HASH` is a lazy static compiled from `"(mod () ())"`.
  - Spending secrets derived: `coin_secret = hash("veil_stealth_nullifier_v1" || shared_secret)`, then `serial_number = hash(coin_secret || "serial")`, `serial_randomness = hash(coin_secret || "rand")`.

##### Key Types
- `StealthKeys` -- view + spend private keys.
- `StealthAddress` -- view + spend public keys (64 bytes total, 32 each).
- `StealthViewKey` -- view private key + spend public key.
- `StealthPayment` -- result of creating payment: puzzle_hash, nonce, shared_secret, puzzle_source.

##### Nonce Derivation
- `derive_nonce(nonce_index)` -- deterministic: `hash("veil_stealth_nonce_v1" || view_privkey || index_le)`.
- Enables wallet recovery from seed + nonce indices.

##### Scanning
- `try_scan_with_nonce(puzzle_hash, nonce)` -- derives shared_secret, checks puzzle_hash == STEALTH_NULLIFIER_PUZZLE_HASH.
- `try_scan_with_tag(puzzle_hash, nonce, expected_tag)` -- additionally verifies 4-byte tag derived from shared_secret.

**Invariants**:
1. Public keys are hash-derived from private keys: `pubkey = hash("stealth_pubkey_v1" || privkey)`. No EC math.
2. Same nonce_index with same keys always produces same payment.
3. Different receivers produce different shared_secrets from same nonce.
4. Viewing tag = first 4 bytes of `hash("veil_stealth_tag_v1" || shared_secret)`.

#### 2.3.3 Payment Keys (`payment_keys.rs`)

- Simpler stealth scheme (parallel to wallet/stealth):
  - `PaymentKey::from_privkey()` -- pubkey = `hash("stealth_pubkey_v1" || privkey)`.
  - `derive_stealth_puzzle_hash(receiver_pubkey, nonce)` -- `hash("stealth_v1" || pubkey || nonce)`.
  - Offer key derivation: `child_privkey = hash("offer_derivation" || parent_privkey || index_be)`.
  - Path derivation: sequential `derive_offer_key()` calls.

**Relationship**: Uses same domain separator `"stealth_v1"` as `wallet/stealth.rs` for shared_secret derivation and same `"stealth_pubkey_v1"` for pubkey derivation. These two modules are consistent in their cryptographic derivations.

### 2.4 Simulator

**Location**: `src/simulator.rs`

##### `CLVMZkSimulator`
- Test-only blockchain state machine.
- **Tree depth**: 20 (supports ~1M coins).
- State: nullifier set, UTXO set (keyed by serial_number), merkle tree, commitment-to-index map, transaction log, block height.

##### `add_coin()`
- Computes `CoinCommitment`, inserts into merkle tree, records leaf index, adds to UTXO set keyed by serial_number.
- Returns serial_number.

##### `add_coin_with_stealth_nonce()`
- Same as `add_coin()` but also stores stealth nonce and puzzle source.

##### `spend_coins_with_params_and_outputs()` (main spend flow)
1. Get current merkle root.
2. Determine if ring spend is possible (all same tail_hash + multiple coins).
3. If ring: call `Spender::create_ring_spend()` for single proof.
4. If not ring: call `Spender::create_spend_with_serial()` per coin.
5. Check nullifiers against nullifier set (double-spend detection).
6. Parse CREATE_COIN conditions from proof outputs.
   - **Enforcement**: CREATE_COIN must have exactly 1 arg (32-byte commitment).
   - **Non-condition outputs silently ignored** (e.g., simple return values).
7. Create `SimulatedTransaction`.
8. Add nullifiers to set.
9. Add new coin_commitments to merkle tree.
10. If output coins provided, validate commitment match and add to UTXO set.
11. Remove spent coins from UTXO set.
12. Increment block height.

**Invariants**:
1. Double-spend check: `nullifier_set.contains(nullifier)` -> reject.
2. Serial_number == UTXO key. Removing spent coins uses serial_number, not nullifier.
3. Tree is append-only; spent commitments remain in tree (spent coins are removed from UTXO set but their merkle leaves persist).
4. Serialization: `#[serde(skip)]` on `coin_tree` -- must call `rebuild_tree()` after deserialization.

##### `process_settlement()`
- Adds maker + taker nullifiers (double-spend checked).
- Adds 4 coin commitments to merkle tree.
- Does NOT add coins to UTXO set (settlement coins would need separate tracking).

##### CREATE_COIN Transformation
- `transform_create_coin_conditions()`:
  - 2 args: transparent mode, left as-is.

#### 2.5.3 SP1 Backend (`backends/sp1/`)

##### Host (`src/lib.rs`)
- `Sp1Backend::new()` -- checks ELF availability.
- `prove_chialisp_program()` -- wraps inputs in `CoinMode::Execute`, runs SP1 prover.
- `prove_with_input()`:
  - Host-side guards: reject Mint, reject CAT without tail_source, reject leaf_index > u32::MAX.
  - Optionally skips execution (SP1_SKIP_EXECUTION env var).
  - Proof mode configurable: core, compressed, plonk, groth16.
  - Validates nullifier proof output.
- `verify_proof_and_extract()` -- deserializes bincode, calls `client.verify()`.

##### Guest (`program/src/main.rs`)
- Full guest program running inside SP1 zkVM.
- **Precompiled puzzles**: `DELEGATED_PUZZLE_SOURCE` has hardcoded bytecode and hash to skip guest-side compilation (saves ~500-570s).
- Flow:
  1. Read `Input` from stdin.
  2. Compile Chialisp (or use precompiled).
  3. Create `VeilEvaluator` with SP1-specific crypto functions.
  4. Execute CLVM program.
  5. Enforce ring balance.
  6. Transform CREATE_COIN conditions (2-arg transparent, 4-arg private).
  7. Verify serial commitment, coin commitment, merkle proof (if Spend mode).
  8. Execute TAIL program (if CAT).
  9. Compute nullifier.
  10. Process additional ring coins (same checks).
  11. Commit `ProofOutput` to journal.

- BLS verification in guest: uses `bls12_381` crate with hash-to-curve and pairing.
- ECDSA verification: uses `k256` via `verify_ecdsa_signature_with_hasher()`.

##### Recursive Aggregation (`src/recursive.rs`)
- `RecursiveAggregator::aggregate_proofs()`:
  - Deserializes all child proofs (must be base proofs).
  - Decodes `ProofOutput` from public values.
  - Packs into `RecursiveInputData`.
  - Runs recursive guest ELF.
  - Returns serialized aggregated proof.

#### 2.5.4 RISC-0 Backend (`backends/risc0/`)

- Analogous to SP1 but uses RISC-0 SDK.
- Receipt serialization via `borsh` (not bincode).
- Verification uses guest image ID.
- Same host-side guards as SP1.
- Recursive aggregation and settlement guests provided.

## Phase 3 -- Global System Understanding

### 3.1 State & Invariant Map

#### Global Invariants

| ID | Invariant | Enforced By | Risk if Violated |
|---|---|---|---|
| **I1** | Each coin has unique serial_number (random 32 bytes) | `rand::thread_rng()` in `PrivateCoin::new_with_secrets()` | Nullifier collision -> double-spend or fund loss |
| **I2** | Nullifier = hash(serial_number \|\| program_hash \|\| amount) | `compute_nullifier()` in both host and guest | Double-spend if wrong; fund loss if non-deterministic |
| **I3** | Serial commitment = hash(domain \|\| serial_number \|\| serial_randomness) | `compute_serial_commitment()` | Coin commitment invalid if mismatch |
| **I4** | Coin commitment = hash(domain \|\| tail_hash \|\| amount \|\| puzzle_hash \|\| serial_commitment) | `compute_coin_commitment()` | Merkle proof fails; coin unspendable |
| **I5** | Merkle root changes on every insertion | `SparseMerkleTree::insert()` | Stale roots accepted |
| **I6** | Nullifier set is append-only (no removal) | `CLVMZkSimulator::spend_coins*()` | Double-spend |
| **I7** | Balance: output <= input for ring spends | `enforce_ring_balance()` | Inflation |
| **I8** | All ring coins have same tail_hash | `enforce_ring_balance()` + `Spender::create_ring_spend()` | Cross-asset mixing |
| **I9** | TAIL program hash must match committed tail_hash | Guest TAIL enforcement | Unauthorized CAT spend |
| **I10** | TAIL must return truthy value (not nil) | Guest `is_clvm_nil()` check | Unauthorized CAT spend |
| **I11** | Program hash = hash(compiled_template_bytecode) | `compile_chialisp_to_bytecode()` | Wrong program verification |
| **I12** | Exactly one backend feature enabled | `compile_error!` in `src/lib.rs` | Undefined behavior |
| **I13** | Settlement maker proof must be ConditionalSpend | `prove_settlement()` | Unauthorized settlement |
| **I14** | Guest leaf_index fits in u32 (32-bit RISC-V) | Host-side guards in SP1/RISC0 backends | Guest panic |

### 3.2 End-to-End Workflows

#### Workflow 1: Simple Coin Spend

```
User -> ClvmZkProver::prove_with_serial_commitment()
  -> Backend.prove_with_input(Input { coin_mode: Spend(...) })
    -> [Guest]:
      1. Compile chialisp_source -> bytecode + program_hash
      2. Execute bytecode with parameters -> (output_bytes, conditions)
      3. enforce_ring_balance(inputs, conditions)
      4. Transform CREATE_COIN conditions (4-arg -> commitment)
      5. Verify serial_commitment = hash(serial_number || serial_randomness)
      6. Verify coin_commitment = hash(tail || amount || puzzle || serial_commitment)
      7. Verify merkle_proof(coin_commitment, path, index, root)
      8. If CAT: compile TAIL, verify hash, execute TAIL
      9. Compute nullifier = hash(serial_number || program_hash || amount)
      10. Commit ProofOutput { program_hash, [nullifier], clvm_res }
  -> Host wraps in PrivateSpendBundle
```

#### Workflow 2: Multi-Coin Ring Spend (CAT)

```
User -> Spender::create_ring_spend(coins_vec, merkle_root, tail_source, tail_params)
  -> Verify all tail_hashes match
  -> Compute CoinCommitment for each coin
  -> Pack primary + additional coins
  -> ClvmZkProver::prove_ring_spend()
    -> [Guest]:
      1-9. Same as simple spend for primary coin
      10. For each additional coin: compile, verify commitments, verify merkle, check TAIL
      11. Compute nullifier for each additional coin
      12. Commit ProofOutput with N nullifiers
  -> Verify nullifier count == coin count
  -> PrivateSpendBundle with all nullifiers
```

#### Workflow 3: Settlement (Maker-Taker Offer)

```
--- MAKER ---
Maker -> Spender::create_conditional_spend(coin, settlement_assertion_puzzle, params, ...)
  -> ProofType::ConditionalSpend
  -> PrivateSpendBundle (not submittable alone)

--- TAKER ---
Taker -> prove_settlement(SettlementParams { maker_proof, taker_coin, ... })
  -> Host:
    1. Verify maker proof is ConditionalSpend
    2. Deserialize maker's receipt/proof
    3. Extract maker's journal (ProofOutput)
    4. Parse CLVM output -> (maker_change_commitment, offered, requested, maker_pubkey)
    5. Compute taker's serial commitment
    6. Build SettlementInput
  -> [Settlement Guest]:
    1. Receive SettlementInput
    2. Verify taker's coin (serial, coin, merkle)
    3. Compute payment_puzzle = hash("stealth_v1" || maker_pubkey || nonce)
    4. Compute all 4 output commitments
    5. Commit SettlementOutput
  -> SettlementProof

--- VALIDATOR ---
Validator:
  1. Verify maker's base proof (ZK verification)
  2. Verify taker's settlement proof (ZK verification)
  3. Check consistency (maker journal hash matches)
  4. Add both nullifiers to nullifier set
  5. Add 4 commitments to merkle tree
```

#### Workflow 4: Stealth Payment

```
Sender:
  1. Get receiver's StealthAddress (view_pubkey || spend_pubkey)
  2. Derive nonce deterministically: hash(view_privkey || "nonce" || index)
  3. Compute shared_secret = hash("stealth_v1" || view_pubkey || nonce)
  4. puzzle_hash = STEALTH_NULLIFIER_PUZZLE_HASH (trivial puzzle)
  5. Derive coin secrets from shared_secret
  6. Create PrivateCoin with puzzle_hash, amount, serial_commitment
  7. Encrypt nonce to receiver (out-of-band)

Receiver:
  1. Decrypt nonce from transaction metadata
  2. Derive shared_secret = hash("stealth_v1" || view_pubkey || nonce)
  3. Check puzzle_hash matches STEALTH_NULLIFIER_PUZZLE_HASH
  4. Derive same coin secrets from shared_secret
  5. Can spend using nullifier protocol
```

#### Workflow 5: Recursive Aggregation

```
Host:
  1. Generate N base proofs (each is a complete spend proof)
  2. RecursiveAggregator::aggregate_proofs([proof1, proof2, ..., proofN])
     -> Deserialize each proof, extract ProofOutput
     -> Pack into RecursiveInputData
     -> Run recursive guest ELF
     -> [Recursive Guest]: verify all N base proofs, output AggregatedOutput
  3. Single aggregated proof replacing N proofs
```

### 3.4 Complexity & Fragility Clusters

#### Cluster 1: Settlement CLVM Parsing (HIGH COMPLEXITY)

**Files**: `src/protocol/settlement.rs` lines 401-609

The `parse_maker_clvm_output()` function and its helpers (`extract_create_coin_commitment_host`, `extract_settlement_terms_host`) perform deeply nested pattern matching on `ClvmValue` trees. This is:
- Fragile: any change to the settlement assertion puzzle format breaks parsing.
- Duplicated: coin commitment computation is reimplemented inline (not using `compute_coin_commitment()`).
- Branching: each level of nesting has its own error variant.

**Assumptions**:
1. Maker's CLVM output is exactly `((51 puzzle amount serial rand) (offered requested pubkey))`.
2. All numeric values are atoms (not cons pairs).
3. All 32-byte values are exactly 32 bytes (no leading zero stripping by CLVM).
4. Tail_hash for maker's change coin is the `goods_tail_hash` parameter.
5. The coin commitment computation uses the SAME domain separators as `compute_coin_commitment()`.

#### Cluster 2: Mock Backend Faithfulness (MEDIUM COMPLEXITY)

**Files**: `backends/mock/src/backend.rs`

The mock backend reimplements the entire guest logic on the host side. Any divergence between mock and real guest programs creates test/production gaps. Key areas:
- Balance enforcement
- CREATE_COIN transformation
- TAIL enforcement
- Nullifier computation
- Serial/coin commitment verification
- AGG_SIG validation (uses ECDSA in mock, could be BLS in real backends)

**Invariant**: Mock MUST produce identical `ProofOutput` values (except proof_bytes format) as real backends for the same inputs.

#### Cluster 3: Cross-Platform Serialization (MEDIUM COMPLEXITY)

Multiple serialization formats in play:
- `borsh` -- RISC-0 receipts, `ProofOutput` serialization
- `bincode` -- SP1 proofs
- `serde_json` -- simulator state persistence, CLI wallet data
- CLVM binary format -- program bytecode, condition outputs

The `Input` type derives both `serde` and `borsh`. `ProofOutput.proof_type` is `#[borsh(skip)]`. `leaf_index` is `u64` everywhere for 32-bit guest compatibility.

**Assumption**: All serialization formats are deterministic (same input -> same bytes). Borsh is deterministic by spec. Bincode's determinism depends on version/config.

#### Cluster 4: Stealth Address / Payment Key Dual Systems (LOW-MEDIUM)

Two parallel implementations exist:
- `src/wallet/stealth.rs` -- full stealth address system with HD nonce derivation, scanning, tags.
- `src/payment_keys.rs` -- simpler stealth with puzzle hash derivation, offer key paths.

Both use the same domain separators (`stealth_v1`, `stealth_pubkey_v1`). The `payment_keys.rs` module uses `derive_stealth_puzzle_hash()` which derives a puzzle hash, while `wallet/stealth.rs` uses a fixed trivial puzzle hash for all stealth coins.

**Potential confusion**: Two different approaches to stealth payments coexist. Settlement uses `payment_keys.rs` style (hash-based puzzle derivation), while wallet operations use `wallet/stealth.rs` style (nullifier-mode trivial puzzle).

#### Cluster 5: Condition Parsing Edge Cases (LOW-MEDIUM)

**Files**: `clvm_zk_core/src/lib.rs` (lines 470-557)

- `clvm_value_to_conditions()` -- distinguishes single condition vs list by checking if first element is atom or cons.
- `extract_args_from_list()` -- only accepts atoms as args; nested cons pairs in args cause error. This means programs that return deeply nested condition structures may fail parsing.
- `PrivateSpendBundle::extract_created_coins()` -- silently ignores CREATE_COIN with unexpected arg counts (not 1, 2, or 4).

#### Cluster 6: Merkle Tree Performance (LOW -- simulator only)

- `SparseMerkleTree::compute_root()` calls `compute_node_hash(0, depth, hasher)` which is recursive.
- Each insertion triggers full root recomputation.
- `compute_node_hash()` is O(2^level) at each level -- total O(n * depth) per insertion where n = number of leaves.
- For 1M coins at depth 20, each insertion touches up to 1M leaf hashes. This is only used in the simulator.
